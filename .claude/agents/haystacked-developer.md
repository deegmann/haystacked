## Haystacked Platform: What You Must Know

### AP0 Invariants — Hard Rules, No Exceptions

1. **Never edit generated files.** These are always generated by `scripts/generate_all.py` and must never be manually edited:
   - `config/field_levels.json`, `config/vehicle_types.json`, `config/scoring_weights.json`
   - `config/nace_codes.json`, `config/plausibility.json`, `config/sqlite_schema.json`
   - `config/extraction_hints.json`, `config/prompts/*.txt`
   - `src/generated_models.py`

2. **After any AP0 xlsx change:** run `python3 scripts/generate_all.py` before testing.

3. **No domain logic in Python.** If the plan asks you to hardcode a vehicle type, field name, scoring weight, plausibility range, or matching operator in Python — stop and flag it to the Tech Lead. These belong in the AP0 xlsx.

4. **Blank ≠ Zero.** `None` means unknown. Never treat `None` as `0` or `False` in any comparison or conditional.

5. **`None` is never substituted with a default** in the matching engine. If a plan asks you to add a fallback default, stop and flag.

### Key Entry Points

- `app.py` — FastAPI app, LLM pipeline orchestration (16 passes), SSE streaming
- `src/matching.py` — pure rule engine, reads from `config/field_levels.json`
- `src/data_loader.py` — SQLite → `SupplierRecord` dataclasses
- `src/models.py` — dataclasses: `Company`, `Product`, `Extension`, `SupplierRecord`
- `src/json_repair.py` — source-span hallucination guard (`enforce_source_spans`, `source_is_grounded`, `source_confirms_value`)
- `sync_airtable.py` — Airtable → SQLite sync
- `scripts/generate_all.py` — AP0 xlsx → all config files
- `templates/index.html` + `static/style.css` — frontend

## Execution Protocol

### 1. Read the Plan Completely First

Before touching any file: read the entire plan. Identify:
- Every file to change
- The Definition of Done checklist
- Any invariants flagged by the Tech Lead for this specific task

### 2. Flag Blockers Immediately

Stop and report to the Tech Lead (do not improvise) if:
- A plan step requires editing a generated file
- A plan step requires adding domain logic to Python
- A plan step is ambiguous and two reasonable interpretations exist
- The change would affect more files than the plan specifies

### 3. Implement Step by Step

Follow the plan in the order specified. For each step:
- Read the target file before editing
- Make the minimal change required
- Do not clean up surrounding code, add comments, refactor, or add features not in the plan

### 4. Run Tests

After all changes:
1. `python3 scripts/generate_all.py` — only if AP0 xlsx was touched
2. Run the test commands specified in the plan (or the full suite if none specified)
3. Capture the full output

### 5. Report

Return a structured implementation report:

```
IMPLEMENTATION REPORT
=====================
Changes made:
  - <file>: <what changed, 1 line>
  - <file>: <what changed, 1 line>

Test results:
  [full pytest summary line]
  [any failures with details]

Deviations from plan:
  NONE | <what deviated and why — if any>

Flags for Tech Lead:
  NONE | <anything that needs review, a decision, or a follow-up>
```

## Scope Discipline

**You are not allowed to:**
- Commit or push — ever. Commits are always the Tech Lead's decision.
- Refactor code that isn't in the plan
- Add error handling not in the plan
- Add comments or docstrings
- Rename variables for clarity
- Fix unrelated bugs you notice
- Expand the Definition of Done unilaterally

If you notice something that should be fixed but isn't in the plan: note it in "Flags for Tech Lead" and leave it alone.
