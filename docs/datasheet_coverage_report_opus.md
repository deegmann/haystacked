I still left `forks_free_floating` NULL on all three reach trucks pending the ruling, and set it `false` on VNSL14 / `true` on the P and E series where the matrix is unambiguous. **This is the second independent VisionNav document to supply the same evidence** (the first was `1657089341.pdf` p.4's "Perimeter Base Pallet" row).
- **`floor_flatness_req` — 13 more instances, a 3× spread inside one catalog.** ±3 mm/m² (R series, p.13 — the tightest requirement in the whole corpus), ±5 mm/m² (SL/ST/P/E20/Q), ±10 mm/m² (VNE30/35/40, p.15). The four categorical allowed values cannot hold any of them; all 13 left NULL.
- **A capability matrix that AP0 has no home for.** p.7 is a 6-series × 11-criterion load-type × application matrix and it is **invisible to text extraction** (pdfplumber linearises it into a column of orphaned tick marks; it only becomes readable as a render). It is the only place in the entire VisionNav corpus that states, per series, which load carriers and applications each machine is qualified for — it is the source for `load_type`, `station_applications`, `trailer_loading`/`trailer_unloading`, `outdoor_capable` and `forks_free_floating` throughout this group.
- **Load-type mappings with no clean AP0 target** (both applied with per-product notes, both worth challenging): *"Pallet CHEP cerrado"* → `Pallet ISO` (the catalog's own reference load is 1200×1000 mm; AP0 has no closed-bottom-pallet concept); *"Jaula de almacenaje/estantería multicapa"* (mesh storage cage / multi-layer stillage) → `Bulk Bin`. A third, *"Materiales sin soporte"* (unsupported / pallet-less material, ticked for P and E series), has **no allowed value at all** and was dropped.
- **Recurring gaps reconfirmed with 13 fresh instances each:** vehicle **dead weight** (500–6200 kg, printed for every model); **battery voltage architecture** (24 V / 48 V / **83.2 V** — the VNE30/35/40 pack is the first 83.2 V system seen in the corpus, and `battery_type` cannot hold it); **max joint/groove width** (30–50 mm) and **max obstacle/step height** (10–30 mm), printed on every page.
- **`max_speed` 2.7 m/s (VNE20, p.14) exceeds this project's fallback sanity bound of 2.5 m/s** — but `config/plausibility.json` has **no `max_speed` entry at all**, and the source prints *"2.7m/s (6.04mph)"* where 6.04 mph = 2.70 m/s, an internally consistent imperial cross-check. The figure is real, not an OCR slip, and the page itself claims this model *"es capaz de desplazarse a mayor velocidad"*. Worth adding a `max_speed` range to `plausibility.json` with a ceiling above 2.7.
- **`fleet_management_system` limitation, again.** RCS 2.0 is a named proprietary controller that also exposes a documented REST API (p.5: *"Protocolo API Restful Web"*). The single-select cannot express "proprietary product with an open API". Left NULL.

### Group 2 — Hikrobot, full-line Mobile Robot Product Catalog

`AGV_Brochure_(Full_Version)_ENG_2026Q2-V1_READ_updated_16_Jun_2026.pdf` · 69 pp · document code **R.101.EN.26Q2.1** (p.69) · findings → `docs/research_findings_opus_20260808_hikrobot_full_catalog.json`

**This is the largest single yield of the entire corpus.** Deferred across 4+ consecutive sessions on size grounds and never opened. It contains **15 specification tables covering 73 distinct model numbers across 11 product families**, against a DB holding 10 Hikrobot products. Result: **73 products — 69 new / 1 enrich / 3 conflict** (46 Mobile AMR, 21 Forklift AGV, 6 Tugger AGV).

**Method note worth reusing:** I built a page map first (character count + first four lines per page) instead of reading linearly. That located all 15 spec tables in one pass and showed pp.1–17 and pp.51–69 to be marketing and case-study content with no vehicle specifications — the technical content of a 69-page catalog lives on 15 pages. Unlike the VisionNav catalog, **no page of this document required rendering**; every spec table extracted cleanly as pdfplumber text.

**New supplier candidates:** none — Hikrobot already exists (`348154cf-cd2a-4cea-88d5-c79f2b4d3bb8`).

**Conflicts flagged (never resolved, never overwritten):**
- **`max_payload` F5-1600 — DB 1600 vs 1350** (p.26, row *"Rated load (kg)"*). **The model name says 1600 and the spec table says 1350.** This is the identical failure mode found the same day in VisionNav's VNP20 (name implies 2000, table says 1900) — *a payload read off a model number rather than a spec row is now a documented cross-supplier error class.* `max_payload` is `KO_IF_LT`, so an overstated value wins tenders the truck cannot serve. Same product also: DB `lifting_height` 3000 vs catalog 4500. DB `max_speed` 1.5 confirmed.
- **F3-1500 — three conflicts** (p.24): `max_speed` DB 2.1 vs 1.5; `min_aisle_width` DB 2100 vs 2213; `vehicle_width` DB 870 vs 863. `vehicle_length` 1632, `lifting_height` 200, `stop_accuracy` 10, `drive_type` Pallet Mover and `stacking_capability` 0 all confirmed exactly. Note the sibling **F3-1000 *is* rated 2.0 m/s**, so the stored 2.1 may be a mis-attributed sibling value. `min_aisle_width` is `KO_IF_GT` — a stored 2100 against a real 2213 wins aisles the truck does not fit.
- **F4-1000C — a NAMING problem, not a data problem** (p.22). Six values disagree at once (`lifting_height` 2031 vs 2000, `min_aisle_width` 2050 vs 2181, `max_speed` 1.8 vs 1.2, `stop_accuracy` 5 vs 10, `vehicle_length` 1600 vs 1653, `vehicle_width` 800 vs 990) while `max_payload` and `charge_time` agree. **Six simultaneous disagreements is not the shape of a data-entry error, it is the shape of two different machines** — and the catalog's model is `F4-1000`, without the DB's `C` suffix. The DB row's own description also cites a derate ("1000kg at 1.3m, 600kg at 3m") and a 3000 mm reach this table does not show. **Answer the naming question before applying any value.**

**Confirmed (the DB was right):** `Q7-1000E` (p.18) — `max_payload` 1000 and `max_speed` 2.0 both exact. Filed `enrich`.

**Partial coverage — 6 of 10 existing DB products are NOT in this catalog:**
`F1-1000U-A`, `F1-300T-A`, `Q2L-300A`, `Q3-600C`, `Q7-1000D`, `Q7-1500D`. In three cases the catalog carries a **sibling with a different suffix** (Q2-400D vs Q2L-300A; Q3-600D/Q3S-600A vs Q3-600C; Q7-1000E/Q7-1500E vs Q7-1000D/Q7-1500D), which is the classic superseded-model signature. Per project convention these are candidates for review — flagged only; nothing deactivated or deleted.

**The scoping question to decide before importing any of this.** 73 products is a large claim against a 10-product incumbent, and Hikrobot's range does not partition cleanly into AP0's three `product_type` values:
- The **TP6 STU series** (5 models, p.37) are 12-metre-tall, aisle-bound, **busbar-powered** tote robots. The catalog itself says they are *"actively replacing traditional Miniload/palletizer systems"* — they are closer to an ASRS shuttle than a free-roaming AMR. Typed Mobile AMR because nothing else fits; a reasonable decision is that they are not Products in this database at all.
- The **CH cantilever robots** (3 models, p.43) handle reels and spools on a cantilever arm. AP0's `load_type` has no allowed value for a reel/roll/spool — `load_type` is NULL on all three.
- The **CT series** (4 models, p.41) drive *under* a cart (260–320 mm tall) and lift a traction pin into it. Typed Tugger AGV on the strength of *"Conveying type: Traction"* — but **CT7L-1000 has no traction pin at all** (both pin rows read `/`), so that one model's classification is genuinely uncertain.

**Genuinely ambiguous, no value proposed:**
- **`service_coverage`.** p.3: *"Business covers 50+ countries, with branches founded in the Netherlands, France, Germany, Hungary, Korea, Japan, Singapore, and Malaysia."* That yields four unambiguous EU ISO codes (NL/FR/DE/HU), but the DB holds a blanket `EU` on every Hikrobot row. Not proposed as a change — *"branches founded in"* is a sales statement, not a service guarantee, and narrowing `EU` to four countries could wrongly disqualify the supplier.
- **`fleet_management_system`.** The DB holds the non-conforming string `'Proprietary (RCS 2000)'` on two rows. This catalog **never names "RCS 2000"** — pp.7/13 describe the scheduling layer generically and p.4 dates *"Released RCS and iWMS"* to 2016.
- **`vda5050_compatible`.** The string "VDA 5050" does not appear anywhere in these 69 pages. The DB holds `1` for Q3-600C; this document neither supports nor contradicts it. Silence is not evidence.

**Source-document defects (affect trust, not values):**
- p.28 (F6-2000): the speed row is labelled `(mm/s)` but prints `1.5`. Every sibling FMR table labels the same row `(m/s)`, and 1.5 mm/s would be absurd. Read as 1.5 m/s.
- p.31 (F2 tuggers): same mislabel — row reads `(mm/s)` and prints `1.6`; p.30 confirms *"maximum steady running speed up to 1.6m/s"*.
- p.24: the *"Min rotation radius"* row prints only **five** values across **six** model columns, so F3P-3000's radius cannot be attributed.
- p.18 (Q1P-50B): the dimension cell reads `650*450/489*380`, malformed for an L×W×H row. `min_ground_clearance` left NULL rather than guessed.
- p.35 (TP5): dimension cells pack two or three alternative machine sizes into one cell (e.g. `1730*950*4330/1870*1050*4405/2050*1150*4440`). `vehicle_length` and `vehicle_width` deliberately not recorded for the whole family — only height, which `min_ground_clearance` needs.
- p.36 vs p.37 (TP6): the marketing page claims 3.5 m/s and 2 m/s lifting; the spec table says 3000 mm/s and 1500–2000 mm/s. Table used.
- p.30 vs p.31 (F2): p.30's feature list claims *"Omnidirectional movement … moving in oblique line"* while the table's `Motion method` row says only *"Forward, backward, curve, and rotation in place"* with no lateral travel. The two contradict; `omnidirectional_movement` left NULL.

### AP0 findings — Hikrobot group

- **Unit conversion was the dominant risk in this file, at scale.** Every speed row in the catalog is printed in **mm/s** against AP0's **m/s** (73 conversions), and every charge-time row is printed in **hours** against AP0's **minutes** (68 conversions). An unconverted value would be off by 1000× or 60×. Both printed and converted figures are in every citation. On the positive side, `charge_time` here is a clean absolute duration — **none of the four known traps** (ratio, partial 20→80 % charge, current in amperes, C-rate) appears.
- **`min_ground_clearance`'s name-vs-meaning trap is unusually dangerous in this document.** The field holds the ROBOT HEIGHT (AP0 hint: *"Source: vehicle height spec"*) — but **seven** of these fifteen spec tables print an actual row literally called **"Chassis ground clearance"** (15–40 mm) sitting immediately beside the dimension row. Taking that row would have written a 20–40 mm value into a K.O. field that should hold 250–2750 mm, on dozens of products. Left unmapped throughout; it has no AP0 field of its own. **This is the strongest argument yet for renaming the field.**
- **`rotation_capable` — the mis-mapping trap, five more opportunities declined.** Five tables carry a *"Rotation capacity: 360° in-place rotation"* row. That is the VEHICLE spinning; AP0's `rotation_capable` means rotating the CARRIED RACK to present a face. Left NULL on all 73 products; holonomic capability recorded in `omnidirectional_movement` instead. Note the DB already holds `rotation_capable = 1` on five Hikrobot LMR rows — not contradicted here, but not supported either.
- **Scope asymmetry, 14 fresh instances in one document.** Every CTU and STU model publishes an explicit **"Aisle width"** row (800–1300 mm), but `min_aisle_width` exists only in Forklift and Tugger scope, never AMR. For the TP6 STU — a machine *sold on* narrow-aisle storage — losing its aisle figure is a substantive loss, not a cosmetic one.
- **Three more scope-asymmetry instances, each a different field:**
  - `busbar_compatible` is Forklift-scope only (written for VNA trucks), yet the TP6 STU **literally runs off a sliding-contact busbar** (p.37 `Power supply method: Sliding contact`) and therefore has *no* battery fields at all.
  - `special_fork_option` has a `Telescopic` allowed value but is Forklift-scope only — **CHF-50** (p.43) is an AMR with an explicitly *"Telescopic fork"* execution structure and cannot record it.
  - `min_ground_clearance` (in its literal sense) is AMR-scope only, so the **F2 tuggers'** genuine published ground clearance (25/30 mm, p.31) has nowhere to go.
- **A new K.O.-relevant field with no AP0 home: hand-over deck height.** The CU conveyor robots (p.39) publish *"Working surface height (from ground)"* (400–1200 mm) and the CH robots (p.43) publish it as a range (260–1100 mm). That is precisely the dimension that decides whether the robot can mate with a fixed conveyor — a genuine integration K.O. — and there is no field for it.
- **A two-stage accuracy that AP0 can only half-record.** The HC family (p.47) publishes both *"Positioning accuracy ±10 mm"* and *"Secondary docking accuracy ±1 mm"* — a ten-times-tighter figure for the final approach to a machine. AP0 has one `stop_accuracy` slot per product, so a genuinely differentiating capability is lost. The CH family does the same (±10/±5 positioning vs ±2/±2.5/±5 docking). Several suppliers publish two-stage accuracy; it may warrant a second field.
- **Payload-vs-lift-height derating, made visible as two model numbers.** `F4-1500` carries **more** (1500 kg) but lifts **less** (1300 mm) than `F4-1000` (1000 kg / 2000 mm) on an otherwise **identical chassis** — same L×W×H, same Ast, same speed, same turning radius (p.22). This is the clearest single illustration in the corpus of the derating relationship AP0 cannot express: here the manufacturer solved it by shipping two SKUs.
- **A VNA edge case that would mis-fire the K.O.** The omnidirectional QF3 models need only a **1500 mm** aisle (p.20, corroborated on p.19: *"omnidirectional AMR with national standard pallets (1.2m*1m) requires picking aisle to be only 1.5m"*) — **below the 1800 mm figure AP0's `vna_capable` hint uses as the VNA threshold** — yet they are pallet movers, not turret trucks, so `vna_capable = false`. A VNA tender would therefore exclude, via `KO_BOOL_EXCLUSIVE`, a machine that physically fits the aisle. Worth a look: VNA is defined by *turret technology*, but the hint defines it by *aisle width*.
- **`config/plausibility.json` floors rejected legitimate products again, twice.** All six QF3 models lift **335 mm** against `required_lifting_height.min = 500`; four Q-series LMRs lift **60–79 mm** against `required_lift_height.min = 100`. Same defect shape already recorded for pallet-jack AGVs and omnidirectional AMRs — the DB already holds 100, 115 and 125 in the same field.
- **The heaviest vehicle in the corpus, by a wide margin.** `HL10-10000A` (p.45) is rated **10,000 kg**. It sits inside `required_max_payload.max` (50,000) but far above this project's own rule-of-thumb bands in the agent brief (AMR 50–1500 kg; heavy-duty forklift up to 8,000 kg). Those bands should be widened or annotated to admit heavy-duty AMRs.
- **A CE difference *between two variants of one product* cannot be expressed.** `QF3-1000D-P1` and `QF3-1000D-P1 (CE)` are physically different machines (1250×1100×170 / 1.6 m/s vs 1423×1200×246 / 2.0 m/s, p.20), and the CE variant complies with MD, RED and EMC (p.19). But `certifications_generic` is a **Company-level** field, so a per-variant CE distinction has nowhere to live.
- **`functional_safety_level` — a real loss to an unnumbered claim.** p.4: *"Got SIL & CE Certification: AMR Integrated Safety Controller"*. "SIL" with **no level number** cannot map to AP0's `SIL 2` / `SIL 3`.
- **No field for installed base or market position.** p.4 gives *"100,000 AMRs produced as of May, 2024"*, *"50,000+ AMRs delivered"*, *"Over 1,500 AMR customers worldwide"* and *"Ranked top in global shipments for 3 consecutive years (from Interact Analysis)"*. None of these is a completed-reference-install count, so `reference_count` stays NULL — yet this is the strongest commercial signal in the whole document.
- **`Contour` used as a real allowed value again.** The F3 pallet-truck family (p.23) states *"the whole series adopts environmental **contour** navigation methods"*, so `navigation_type` includes `Contour` alongside `Natural Feature (SLAM)` — following the Grenzebach precedent that the hint's "contour-based → SLAM" rule is tender-side normalisation and would otherwise make `Contour` unreachable. (p.23's separate *"supports texture navigation"* claim is deliberately **not** mapped — the term is never defined and the spec table lists laser SLAM only.)
- **The IBASE platform is a Base-Model modelling question.** pp.16–17 describe *"Intelligent Base … the fourth-generation AMR architecture platform"* with a *"1+N+X"* model (*"Based on one intelligent base, Hikrobot derives N types of AMRs, covering X scenarios"*). That is a genuine shared-platform statement across the whole range — exactly what the Base Model layer exists for — but it is a hardware *architecture* shared across families, not a single base model, so it cannot be one `base_model_id`. Worth reading before the import script author decides base-model grouping.
